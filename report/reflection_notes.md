# Reflection notes (kept as we go; section i of the report is written from these)

Dated, factual notes about what actually happened. Not polished.

## Phase 1

- **2026-11-26: starting question.** "Does rain delay, flatten or worsen Bengaluru's evening PM2.5 peak, and on which weekdays and months is the evening pollution rush worst?" Decision: when to issue evening pollution alerts, and whether rain-day rules need different timing.
- **2026-11-26: build environment.** The scaffold was written in a sandbox that could not reach api.openaq.org or archive-api.open-meteo.com (blocked by its network policy). So no source has been confirmed yet. The smoke test (`src/00_smoke_test.py`) has to be run on a teammate's laptop after M1. Lesson: "test that each API actually returns data" is a real step, not a formality.
- **2026-11-26: OpenAQ docs check.** The docs give the query-parameter spelling as `datetimeFrom` in one place, while the API reference uses `datetime_from`. To avoid trusting a silently ignored filter, both scripts check that the returned timestamps fall inside the requested range.
- **2026-11-26: Google Trends granularity.** For a 14-month range Trends returns weekly values, not hourly. So Trends can only add context at the week level. It cannot explain individual evenings.
- **2026-11-26: first real smoke test (teammate laptop, Arch Linux).** Open-Meteo PASS: 24/24 hours on 2025-10-01, and `boundary_layer_height` is available. OpenAQ: the key works and 25 locations were found, but the first monitor picked ('Peenya, Bengaluru - KSPCB', sensor 13852) had 0 hours on 2025-10-01. The empty result (not an error) suggests the date filter works and this sensor id is stale. That is our first "station ID change" case. The smoke test now only tries monitors whose first/last dates span the test day.
- **2026-11-26: smoke test passes.** 25 locations in the box, 21 PM2.5 monitor/sensor pairs, and 17 sensors active on 2025-10-01 across 10 distinct stations. Most stations carry two PM2.5 sensor ids (an old 5-digit id and a new 1223xxxx id), so a "station" ≠ a "sensor". BTM Layout returned 0/24 hours on 2025-10-01 for both ids, so even active stations have whole-day gaps. OpenAQ hourly periods start at :30 UTC (e.g. 2025-09-30T23:30Z), which is exactly :00 IST. So the hours are IST-aligned, which helps the UTC→IST conversion check.
- **2026-11-26: coverage reality check.** We planned 6–10 stations at ≥70% coverage, but only 5 passed: Jayanagar 85.6, Hombegowda Nagar 85.5, Hebbal 79.5, Silk Board 78.2, Bapuji Nagar 70.9. BTM Layout (68.2) and Peenya CPCB (61.9) were just below, and the three stations added in Feb 2025 sat at 38–51%. All old 5-digit sensor ids were 0% in range. The team chose a 60% rule (7 stations), relying on the per-evening gap rule to drop incomplete evenings. This is the first time the data changed our plan.
- **2026-11-26: collection done.** OpenAQ: 204,584 hourly rows (co 48,952; no2 51,290; pm10 51,498; pm25 52,844) across 7 stations, in about 11.5 minutes. The per-sensor PM2.5 counts match the coverage % from the station finder (e.g. Silk Board 7,804 / 9,984 = 78.2%). Open-Meteo: 9,984 hourly rows (416 days × 24), no variables missing.
- **2026-11-26: what an OpenAQ "hour" is.** Each hourly value is the average of the 15-minute CPCB/KSPCB readings (coverage.expectedCount 4, observedCount 0–4). Each record carries both a UTC timestamp ("…T23:30:00Z") and an IST one ("…T05:00:00+05:30") for the same moment. This gives us a built-in check on our own UTC→IST conversion.
- **2026-11-26: units surprise.** OpenAQ delivers NO2 and CO in **ppb**, not the µg/m³ (NO2) and mg/m³ (CO) that CPCB and the Indian AQI use; PM2.5 and PM10 arrive in µg/m³. We convert at 25 °C and 1 atm, and record that assumption.
- **2026-11-26: the half-hour problem.** Air-quality hours start at :00 IST (:30 UTC), but Open-Meteo hours start at :00 UTC = :30 IST. A naive join on the hour would pair each reading with weather 30 minutes off. We align instantaneous variables by the mid-hour label, and split rain totals half-and-half. This is the brief's "lining up the same hour is most of the work", made concrete.
- **2026-11-26: gaps and outliers on real data.** The full grid has 279,552 station-parameter-hours, and 75,136 (27%) were never sent. PM2.5 was recorded for 76% of station-hours. The gap heatmap shows a ~2-week white band in late Jan 2026 across **all 7 stations at once**, which looks like a feed outage (CPCB/OpenAQ) rather than sensor failures. There are also long single-station outages: Peenya Jun–Aug 2026 (longest PM2.5 gap 1,491 h ≈ 62 days), BTM Layout Aug–Sep 2026 and Bapuji Nagar Nov–Dec 2025. Failures: 1,720 flat-line hours (931 of them PM10), 877 exact zeros (439 PM2.5), 10 spikes, 1 out-of-range. No 999/9999 codes and no negatives were found. Kept as real: 145 festival-night extremes and 65 city-wide extremes; 806 extremes stay unexplained and the top 10 go to human review. 872 of 2,912 station-evenings (30%) are too incomplete to time the evening peak.
- **2026-11-26: two Spark time traps, found in testing.** (1) Spark cannot read pandas' nanosecond timestamps ("Illegal Parquet type: INT64 (TIMESTAMP(NANOS,false))"), so all parquet files are now saved in microseconds (`save_parquet` in common.py). (2) `date_trunc` silently returns a time-zone-AWARE timestamp. Written to disk, it read back 5.5 hours off in pandas. We cast it back to `timestamp_ntz`, and the job now checks that saved hours match Spark's hours. Same lesson as the brief: time is the hard part.
- **2026-11-26: first real SQL results changed the analysis plan.** Q4: evening PM2.5 in rain hours is ~21–23 µg/m³ vs ~33–39 dry, but rain is mostly monsoon, so this raw gap mixes rain with season; we must compare within month × day type. Q7: the "evening peak" is spread out. 20:00 is the most common peak hour (468 station-evenings), but 23:00 (the window edge) is second (387), so on many nights PM2.5 is still rising at midnight (the night-time boundary-layer "lid"), not peaking with traffic. We now report edge peaks separately instead of pretending every night has a clear 8 PM peak.
